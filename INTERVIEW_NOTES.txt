ASCEND — AI LEARNING WORKSPACE

--------------------------------------------------------------------------------
1. PROJECT OVERVIEW (IN SIMPLE LANGUAGE)
--------------------------------------------------------------------------------

Ascend is a single web app that replaces the pile of separate tools a learner
normally juggles — one app for study plans, one for flashcards, one for PDF
notes, one for finding YouTube tutorials, a spreadsheet for interview prep,
a separate calendar, a separate to-do app — with one connected workspace.

The core idea is "Spaces." A Space is a chat-driven workspace built around one
learning goal (e.g. "Learn React", "Become a Data Scientist"). Inside a Space
the learner talks to an AI assistant in a chat box, and that assistant can
generate real, saved content for them: a structured study roadmap, a visual
mind map, a flashcard deck, insights from an uploaded PDF, curated YouTube
videos, or a prioritized to-do list — all without leaving the conversation.

Everything generated inside every Space also surfaces in three cross-cutting
views so the learner never has to remember which Space something lives in:
  - Memory: every roadmap, mind map, flashcard deck, and document, in one library.
  - Task List: every to-do task, sorted by priority, across every Space.
  - Calendar: a day/week/month calendar showing when roadmap tasks are
    scheduled and when to-do tasks are due.

Outside of Spaces, there's a Dashboard (streaks, study hours, weekly activity),
a Career Intelligence section (upload a resume, get a skill-gap analysis and
interview practice questions for a target role), authentication, and settings.

There's also a small automated layer on top of all of this: Email Monitoring,
which (with the learner's permission, via Gmail OAuth) reads their inbox and
turns anything actually actionable — an interview that got scheduled, an
exam date, a deadline — into a task, without the learner having to manually
enter it. Everything else in the inbox (newsletters, receipts, marketing) is
read, classified as irrelevant, and never shown — explained in full in
section 9 below.

Two more autonomous/AI-heavy features round this out:
  - Weekly Plan: one click deterministically rebalances the learner's overdue
    and this-week to-do tasks across the next 7 days (max 3 a day, real
    database writes, not just a suggestion), then Gemini writes a short,
    specific recap of the resulting week.
  - Ask Your Documents: real retrieval-augmented generation (RAG) over every
    PDF the learner has ever uploaded — pgvector similarity search finds the
    most relevant passages across all their documents, and Gemini answers
    using only those passages, with numbered citations back to source.
Both are covered in full in section 9.

Nothing on the site is faked to look finished. If no AI key is configured, AI
features fall back to a clearly-labeled "demo" mode that still works end to
end using deterministic logic — so the product always demos honestly, and
never silently pretends a feature is doing something it isn't.

2. TECH STACK
--------------------------------------------------------------------------------

FRONTEND
  - React 18 + TypeScript (strict mode — no loose "any" types)
  - Vite — build tool and dev server
  - Tailwind CSS v4 — utility-first styling, CSS-first theme config
  - React Router v7 — client-side routing
  - TanStack Query (React Query) — all server-state fetching/caching/mutations
  - Zustand — small amount of local UI state (sidebar collapsed, etc.) — NOT
    used for server data, to avoid having two sources of truth
  - Lucide React — icon set
  - Recharts — dashboard charts
  - react-markdown + remark-gfm + remark-math + rehype-katex — renders AI
    output as formatted markdown, including math formulas (KaTeX) and diagrams
  - @tailwindcss/typography — real heading/paragraph/list hierarchy for that
    markdown (headings actually look like headings, lists actually indent) —
    registered via Tailwind v4's CSS-first `@plugin` directive, no JS config
  - react-syntax-highlighter — real syntax-highlighted, copy-to-clipboard code
    blocks for any fenced code the AI returns (study notes, coding interview
    answers) — every AI-markdown surface in the app shares one component
    (AiMarkdown) so this looks and behaves identically everywhere
  - mermaid — renders flowchart/sequence diagrams that the AI sometimes
    includes in study notes
  - date-fns — all date math (roadmap scheduling, calendar grid, task due dates)
  - pdfjs-dist (PDF.js, the engine behind Firefox's built-in PDF viewer) —
    extracts raw text from an uploaded PDF entirely in the browser
  - react-hot-toast — success/error notifications
  - Web Speech API (native browser API, no library) — voice-to-text for the
    microphone/voice input feature

BACKEND / DATA
  - Supabase — this is the entire backend. No custom Node/Express server exists.
      - Postgres — the database
      - pgvector (Postgres extension) — stores a 768-dimension embedding
        per PDF chunk and powers the cosine-similarity search behind Ask
        Your Documents (section 9 below)
      - Supabase Auth — email/password authentication, session management
      - Supabase Storage — stores uploaded PDF files, private per user
      - Row Level Security (RLS) — Postgres-level rules so a user can only
        ever read/write their OWN rows, enforced by the database itself, not
        just by the app's UI (explained more in the Security section below)
      - Supabase Edge Functions — small serverless functions (Deno runtime):
        `ai-complete` proxies general AI requests so a paid API key never
        reaches the browser (explained more below); `classify-emails`,
        `gmail-oauth-callback`, `gmail-fetch-messages`, and `agent-cron-check`
        power Email Monitoring; `document-embed` and `document-ask` power Ask
        Your Documents — all explained in section 9.
  - Gmail API (OAuth 2.0, read-only scope) — Email Monitoring's data source,
    opted into per learner via a standard Google OAuth consent flow, never
    scraped or accessed without explicit permission.

AI
  - Google Gemini (model: gemini-2.5-flash) — the only real AI provider wired
    in. All AI calls ask Gemini to return structured JSON matching an exact
    shape, which is parsed straight into TypeScript objects.
  - A parallel "mock AI service" — deterministic, rule-based logic that
    produces realistic-looking (clearly labeled as demo) output with zero
    API key required, so the whole app is explorable with no setup.

TESTING
  - Vitest — test runner (integrates directly with the Vite config)
  - @testing-library/react + @testing-library/user-event — component tests
  - 100+ automated tests covering: spaced-repetition scheduling math, roadmap
    date scheduling, mind-map tree layout, calendar grid generation, the
    chat-flow's natural-language parsing helpers, the task-priority parsing
    heuristic, and both AI service implementations (including Gemini's
    request/response handling with the network mocked out — no test ever
    makes a real, billed API call)

TOOLING
  - ESLint + typescript-eslint — linting
  - GitHub Actions — CI pipeline that runs lint, type-check, tests, and a
    production build on every push

3. ARCHITECTURE, EXPLAINED SIMPLY
--------------------------------------------------------------------------------

This is a single-page application (SPA). There is no traditional backend
server that the frontend team wrote — the browser talks directly to Supabase
for almost everything.

  Browser (React app)
     |
     |--- talks directly to ---> Supabase (Postgres database, Auth, File Storage)
     |
     |--- talks directly to ---> YouTube Data API (only for public video search)
     |
     |--- talks to ---> ai-complete Edge Function ---> Google Gemini API
     |                   (this one extra hop exists ONLY to keep the paid
     |                    Gemini key off the browser — see Security section)
     |
     '--- talks to ---> gmail-oauth-callback / gmail-fetch-messages
                         Edge Functions ---> Gmail API
                         (same reasoning: the Gmail OAuth client secret and
                          the encrypted access/refresh tokens never touch
                          the browser — see section 9 and Security section)

  A fifth Edge Function, agent-cron-check, isn't reachable from the browser at
  all — it's meant to be triggered on a schedule (Supabase's own Scheduled
  Triggers, or any external cron) and scans every connected learner's inbox
  using the Postgres service-role key, which is why it's gated by a separate
  shared secret instead of a user login.

Inside the React app, the code is organized in layers, each with one job:

  pages/            One file per screen/route (thin — just wires pieces together)
  features/<name>/  Each product area (roadmaps, flashcards, spaces, career,
                     calendar, tasks, etc.) has its own components/ and hooks/
  services/         The ONLY layer allowed to talk to Supabase or the AI API.
                     Components never call the database directly.
  hooks (TanStack Query)   Wrap the services layer, handle caching, loading
                     and error states, and cache invalidation after a change
  components/ui/    A small design-system (Button, Card, Modal, Input, etc.)
                     shared by every feature so the whole app looks consistent

Why this layering matters (a good interview talking point): because every
Supabase/AI call goes through the services/ layer, swapping the real Gemini
service for the mock one — or later, swapping Supabase for a different
backend — never touches a single component. The UI only ever depends on a
TypeScript interface, never a concrete implementation.


--------------------------------------------------------------------------------
4. EVERY FEATURE, EXPLAINED
--------------------------------------------------------------------------------

AUTHENTICATION
  Email/password sign up and login via Supabase Auth. A Postgres trigger
  automatically creates a matching "profile" row the moment someone signs up.
  Forgot-password sends a reset email; protected routes redirect to /login
  if there's no active session.

DASHBOARD
  A home screen showing: current study streak, total study hours, a weekly
  activity bar chart (Recharts), the learner's active roadmap with progress,
  flashcards due for review today, recently opened documents, and recommended
  videos. All numbers come from a "learning_activity" event log table (every
  completed task, reviewed flashcard, watched video writes one row) — the
  dashboard is a real query over real events, not hand-waved.

SPACES (the core feature)
  A Space is a saved, chat-driven workspace for one learning goal. Opening a
  new Space shows a chat box and a row of "widgets" (Roadmap, Mind Map,
  Flashcards, PDF, Videos, To-do List). The learner can either type a free
  message ("I want to learn React") — which an AI classifier reads and
  automatically decides what to generate — or click a widget directly.
  Clicking a widget starts a short back-and-forth Q&A right inside the chat
  (e.g. for a roadmap: "what's your level?", "any deadline?", "hours per
  day?", "do you have study material to base it on?") before generating the
  content. Generated content ("artifacts") appear as a card in the chat that
  can be opened into a split-screen panel next to the conversation.
  A microphone icon lets the learner speak their answer instead of typing,
  using the browser's built-in speech-to-text.

ROADMAPS
  An AI-generated, structured study plan: phases, each containing tasks, each
  with an estimated number of study hours. Every task has a real date range,
  calculated from the roadmap's creation date, hours available per day, and
  each task's estimated hours — a pure scheduling algorithm, no AI involved
  in the date math itself. Clicking a task shows AI-generated study notes for
  that specific topic (markdown, with LaTeX formulas and diagrams when
  relevant). Selecting a word or short passage inside those notes and
  pressing Ctrl/Cmd+E pops up an instant AI explanation (see AI section below).

MIND MAPS
  A topic is expanded by AI into a hierarchical tree (root → branches →
  sub-points), then laid out automatically on a pannable, zoomable canvas the
  learner can click through to explore or collapse.

FLASHCARDS
  Cards can be generated by AI from a topic or from an uploaded PDF, or added
  manually. Studying uses real spaced repetition — the same category of
  algorithm Anki uses (a simplified SM-2): each review (again/hard/medium/
  easy) adjusts an "ease factor" and the interval until the card is shown
  again, and the card graduates through new → learning → mastered. This is
  math, not AI — no model is involved in the scheduling.

PDF INTELLIGENCE
  A PDF is uploaded, its text is extracted entirely in the browser (PDF.js —
  no server involved in extraction), and that text is sent to the AI to
  produce: a summary, a bulleted list of key points, question/answer pairs,
  a multiple-choice quiz, and flashcards — all from the same source document.

LEARNING VIDEOS
  Search for topic-relevant YouTube videos, filterable by difficulty and
  category. If a YouTube API key is configured, results are live; otherwise
  a curated, hand-picked catalogue of real, well-known educational videos is
  used instead (never invented titles or fake statistics), with a visible
  "Demo data" label so it's never ambiguous.

TO-DO TASK LIST (new)
  A widget inside a Space where the learner brain-dumps everything on their
  mind — by typing or by voice — in one free-flowing sentence, e.g. "I need
  to buy groceries, and then I have an exam next month, and I need to finish
  a pitch deck tonight." The AI splits that into separate tasks, works out a
  real due date for each from today's date, and assigns a priority (high/
  medium/low) based on urgency. Tasks can be checked off or deleted, and show
  up both in the Space they were created in and in the global Task List page.

CAREER INTELLIGENCE
  Pick a target role (or type a custom one), then upload a resume (PDF) or
  paste resume text. The AI reads it and produces: an overall summary, a list
  of strengths, a list of gaps versus the target role, and a rating (0-5) for
  each of the 5-8 skills most relevant to that role — this is the "resume →
  skill calculation" feature, explained in full technical detail in section 5
  below. From there: a skill-gap table the learner can fine-tune by hand, an
  "Improve Skill" button per skill that opens AI-recommended videos, courses,
  study notes, and a 4-question quiz for that specific skill, and an
  interview-prep tab with 18 AI-generated practice questions (technical,
  behavioral, system design, coding, resume, HR) with sample answers.
  Nothing in this section renders until a resume has actually been analyzed
  for that role — no placeholder/fake data is ever shown as if it were real.

MEMORY
  A single library page listing every roadmap, mind map, flashcard deck, and
  document ever generated, across every Space, with a link back to open each
  one in its Space. Content from a deleted Space is automatically removed
  from Memory too (cascading delete), so there are never dead links.

CALENDAR (new)
  A real calendar with Day, Week, and Month views. Month view shows a full
  grid of that month's dates (including the tail end of the previous/next
  month to fill the grid cleanly), correctly recalculated every time the
  learner moves to a different month. It plots two kinds of real, already-
  computed data: every scheduled roadmap task (on its calculated start date)
  and every to-do task (on its due date). Clicking any day jumps straight
  into that day's agenda view.

TASK LIST PAGE (new)
  Every to-do task from every Space, in one place, grouped and filterable by
  priority (All/High/Medium/Low), each showing which Space it came from.

EMAIL (new)
  A dedicated page that shows only what Email Monitoring has decided is
  actually actionable in the learner's inbox — a scheduled interview, an
  exam date, a deadline, a meeting invite — filtered down from everything
  else (newsletters, receipts, marketing, notifications), which is
  deliberately never shown. Clicking "Scan Inbox" pulls the 50 most recent
  emails and classifies all of them (in parallel, a handful at a time, so a
  full scan takes seconds rather than minutes). Each actionable email shows
  a priority badge; clicking it opens a modal with an AI-generated summary of
  what the email is actually about (never the raw body text). Each one can be
  turned into a real to-do task with one click ("Add to Task List"), or all
  of them at once ("Organize into Tasks") — converted tasks get a due date
  spread out by urgency (today for high, +2 days for medium, +5 days for low,
  so the Calendar doesn't get slammed with everything landing on the same
  day) and then show up normally in both the Task List and the Calendar,
  since those are just regular to-do tasks under the hood. Full technical
  explanation in section 9 below.

WEEKLY PLAN (new, on the Dashboard)
  One click ("Generate This Week's Plan") deterministically spreads the
  learner's overdue and this-week to-do tasks across the next 7 days (max 3
  a day) and actually updates their due dates in the database — a real
  action, not just a suggestion — then Gemini writes a short, specific recap
  of the resulting week plus a suggested daily rhythm. Shows a 7-day grid of
  what's due when, distinguishing rescheduled to-do tasks from read-only
  roadmap context. Full technical explanation in section 10 below.

ASK YOUR DOCUMENTS (new)
  A dedicated page (retrieval-augmented generation, i.e. real RAG — not a
  buzzword here) where a learner asks a question in plain English and gets
  an answer grounded in every PDF they've ever uploaded, across all of them
  at once or scoped to just one, with numbered citations back to the exact
  source document for each part of the answer. Full technical explanation
  in section 11 below.

GLOBAL SEARCH
  Cmd/Ctrl+K opens a command palette that searches across roadmaps, tasks,
  flashcards, documents, mind maps, saved videos, and career resources at once.

SETTINGS
  Profile editing and sign-out.

5. WHERE AI IS USED, AND EXACTLY HOW IT WORKS
   (this is the section to know cold for an interview)
--------------------------------------------------------------------------------

IMPORTANT DISTINCTION TO BE ABLE TO EXPLAIN CLEARLY:
This project does NOT train or use any custom machine learning model (no
scikit-learn, no PyTorch, no embeddings database, no classifier). Every
"smart" feature is powered by ONE thing: prompting a large language model
(Google Gemini 2.5 Flash) with carefully engineered instructions and asking
it to return a response in an exact, predefined JSON shape, which is then
parsed directly into TypeScript objects and saved to the database like any
other data. This is sometimes called "prompt engineering" or "structured
output generation" — it's a different technique from classical machine
learning (no training data, no model training step, no accuracy/loss
metrics), and it's the honest, accurate way to describe it if asked.

The one piece of genuinely algorithmic (non-AI) "smart" logic in the app is
the spaced-repetition flashcard scheduler — that's a deterministic formula
(SM-2 style), not AI, and it's worth being able to name that distinction too.

Every AI-touching feature is defined through ONE shared TypeScript interface
(AiService) with two interchangeable implementations:
  - mockAiService — runs with zero configuration, using text-processing
    heuristics (splitting text into sentences, keyword matching, filling in
    hand-written templates) to produce realistic, clearly-labeled demo output.
  - GeminiService — the real implementation, sends a prompt to Gemini and
    parses the JSON it returns.
Which one runs is decided in exactly one place in the code, so every screen
in the app behaves identically whether or not a real AI key is configured —
this was a deliberate architecture decision so the product could be reviewed
and demoed by anyone without needing paid API access.

Here is what happens, feature by feature:

1. ROADMAP GENERATION
   Input: the learner's goal, plus optional level/deadline/hours-per-day and
   (optionally) extracted text from an uploaded PDF.
   The prompt asks Gemini to return a JSON object: a title, description,
   estimated duration, difficulty, and 4-6 phases, each with 2-5 tasks (title,
   description, estimated hours). If study material was provided, the prompt
   explicitly instructs the model to base phases/tasks on what that material
   actually covers rather than generic knowledge of the topic.

2. TASK STUDY NOTES
   Input: the specific task's title/description plus its roadmap/phase
   context. The prompt asks for markdown study notes (a short explanation,
   key terms, examples), told to use LaTeX for any formula and a Mermaid
   diagram if a process/architecture would genuinely be clearer as a picture
   — only when it would actually help, not forced in every time.

3. MIND MAP GENERATION
   Input: a topic. The prompt asks for a nested JSON tree (label +
   children, 4-6 top-level branches, 2-4 children each), which is then
   walked recursively to create the individual node rows in the database
   with an automatically computed pan/zoom layout position for each node.

4. PDF INTELLIGENCE (summary / key points / Q&A / quiz / flashcards)
   Input: the raw text extracted from the PDF client-side (PDF.js). Five
   separate, focused prompts are sent against that same text — this keeps
   each output type simple and reliable to parse rather than one giant prompt
   trying to do five things at once.

5. RESUME ANALYSIS / SKILL-GAP CALCULATION — the exact feature you asked
   about in detail:
   Step 1: The learner either uploads a resume PDF (text extracted in the
   browser via PDF.js, same mechanism as PDF Intelligence) or pastes resume
   text directly.
   Step 2: That raw resume text, plus the target role name (e.g. "Data
   Scientist" or a custom-typed role), is sent to Gemini in one prompt. The
   prompt explicitly instructs the model to act as "an expert career coach,"
   read every line of the resume, and:
     - write a 2-3 sentence overall summary
     - list 3-6 concrete strengths actually found in the resume
     - list 3-6 concrete gaps relative to that specific target role
     - identify the 5-8 skills most relevant to that role, and for each one
       rate the candidate's current level 0-5 and the level typically
       expected for that role 0-5
   Step 3 (the important part): the prompt explicitly says "base every
   judgment strictly on what is actually written in the resume, do not
   invent experience that isn't there." This is the actual mechanism behind
   "how does it calculate skills" — it's not measuring anything numerically
   (no keyword-frequency count, no embedding similarity score); it's an LLM
   doing reading comprehension against explicit instructions not to
   hallucinate, and returning its judgment as a structured number so the UI
   can render it as a progress bar / table row.
   Step 4: The result is saved to the learner's career profile. The "skill
   gap" UI and the "fine-tune your skill levels" table only ever render once
   this real analysis exists for that specific role — before that, a clear
   empty state is shown instead of stale or placeholder numbers.
   Step 5: the learner can manually adjust any AI-suggested skill level
   afterward — the AI's numbers are a starting point, not a locked verdict.

6. INTERVIEW QUESTION GENERATION
   Input: target role + the gaps identified in step 5 above. The prompt asks
   for exactly 18 questions (3 each across technical, behavioral, system
   design, coding, resume, and HR categories), each with a sample answer,
   explicitly weighted toward the candidate's known gaps where relevant.

7. SKILL IMPROVEMENT PLAN ("Improve Skill" button)
   Input: one specific skill name. One prompt returns: markdown study notes
   for that skill, two realistic course recommendations from real platforms
   (Coursera, Udemy, etc.), and a 4-question multiple-choice quiz testing
   that skill.

8. CHAT INTENT CLASSIFICATION
   Input: whatever free-text the learner types into a Space's chat box. A
   small, fast classification prompt decides whether they're asking for a
   roadmap, a mind map, flashcards, or just want to chat — this is what lets
   someone type "I want to become a data scientist" directly into the chat
   and have the right thing happen automatically, without needing to know
   the exact widget/command to click.

9. TEXT-SELECTION EXPLAIN (new — the notes highlight-and-explain feature)
   Input: whatever text the learner highlights inside AI-generated roadmap
   task notes, but ONLY once they press Ctrl/Cmd+E. A pure, non-AI function
   first classifies the selection: exactly one word → "word" mode; up to
   4 sentences → "passage" mode; anything longer → ignored entirely (nothing
   happens, even if the shortcut is pressed) so the feature can't be misused
   to summarize an entire page in one shortcut press. For "word" mode, the
   prompt asks for a short, simple definition plus one example sentence
   showing it used in context. For "passage" mode, the prompt asks for the
   same passage rewritten in 2-3 simpler sentences, as if explaining it to
   someone new to the topic. The result appears in a small popover right
   next to the highlighted text.

10. PRIORITIZED TASK LIST (new — the to-do voice/text feature)
    Input: one free-form "brain dump" sentence, typed or spoken, plus
    today's date. The prompt asks Gemini to split it into individual tasks,
    resolve any relative time phrase ("tonight", "next week", "one month
    after") into a real calendar date based on today's date, and assign a
    priority — "high" for anything due today/tonight, "medium" for anything
    else with a firm date, "low" for anything with no time reference at all.
    The mock (no-API-key) version of this one is worth mentioning
    specifically because it's a genuinely useful heuristic in its own right:
    it splits the sentence on connector phrases like "and then" and on
    periods, scans each resulting clause for urgency words ("tonight",
    "today") and relative-time patterns ("one month after", "in two weeks"),
    resolves those into real dates using date-fns date arithmetic, and
    strips the time-phrase and filler words ("I want to...", "I need to...")
    to produce a clean task title — entirely with regular expressions and
    date math, no AI call at all, so the feature is fully explorable even
    without any API key configured.

11. EMAIL ACTIONABILITY CLASSIFICATION (new — the Email Monitoring feature)
    Input: one email's sender, subject, and body (truncated to 5000
    characters so an unusually long email can't blow out the prompt). The
    prompt explicitly frames the question as "does the recipient need to DO
    or PREPARE something because of this" rather than "is this interesting"
    — deliberately strict, since most of a real inbox is noise, not tasks —
    and asks Gemini to return a learning goal (or an empty string if it's not
    actionable), an urgency level, a one-sentence reason, and a confidence
    score. Only emails scoring confidence > 0.7 AND returning a non-empty
    goal are ever surfaced to the learner; everything else — including a
    genuinely-processed "this isn't actionable" verdict — is stored (so it's
    never re-classified on the next scan) but never shown. Full technical
    explanation, including how the response is validated before being
    trusted, is in section 9 below, alongside how Gmail access is secured.

12. EMAIL SUMMARY (new — clicking an email on the Email page)
    Input: the same stored email body used for classification above. Reuses
    the exact same summarizeDocument prompt that already powers PDF
    Intelligence's document summaries (see item 4) — no new AI capability had
    to be built, since "summarize this body of text" is the same job either
    way. The raw email body is never shown to the learner directly; only the
    generated summary is, inside a modal, alongside the subject and priority.

13. WEEKLY PLAN SUMMARY (new — see section 10 for the full feature)
    Input: the finished, already-scheduled 7-day task list (never asked to
    invent the schedule itself — that part is deterministic TypeScript, not
    AI). The prompt asks for a short recap specific to the actual numbers
    (task count, anything time-sensitive) and a one-line suggested daily
    rhythm. Implemented as one more method on the shared AiService interface
    (mock + Gemini), so it rides on the existing ai-complete Edge Function
    with zero new backend surface for this half of the feature.

14. RAG ANSWER GENERATION (new — see section 11 for the full feature)
    Input: the learner's question plus up to 6 numbered excerpts retrieved by
    pgvector similarity search across their own PDF chunks. The prompt
    explicitly restricts Gemini to answering ONLY from those excerpts, citing
    inline like [1], and instructs it to say plainly when they don't contain
    the answer rather than reach for outside knowledge — the same "don't
    fabricate" discipline as the resume analysis prompt (see item 5), applied
    to retrieved context instead of a single document.

VOICE INPUT
  Not an AI feature by itself — it uses the browser's native Web Speech API
  (SpeechRecognition) to convert speech to text live, in the browser, with no
  network call and no third-party service. The resulting text is simply
  typed into the same chat input the learner could have typed into by hand,
  so everything downstream (intent classification, the to-do parser, etc.)
  treats voice input exactly the same as typed input.


--------------------------------------------------------------------------------
6. WHICH AI MODEL, AND HOW IT'S CALLED (SECURITY-CONSCIOUS DESIGN)
--------------------------------------------------------------------------------

Model: Google Gemini 2.5 Flash (gemini-2.5-flash), Google's fast, low-cost
model tier — a deliberate choice given this is a high-frequency, short-prompt
workload (single JSON responses, not long multi-turn reasoning), where a
faster/cheaper model is the right tradeoff over a larger, slower one.

How it's actually called (a strong interview talking point on security
awareness): the Gemini API key is NEVER present in the browser. Early in
development it was — that's a common mistake, worth being honest about — but
it was corrected: every `VITE_`-prefixed environment variable in a Vite app
gets compiled directly into the JavaScript bundle that ships to the browser,
which means anyone could open the browser's Network tab or read the bundled
JS and steal a client-side key. Since Gemini is a metered, billable API, that
would mean someone could run up a real bill on a stolen key.

The fix: a small Supabase Edge Function (`ai-complete`) was added. It:
  1. Requires the caller to have a valid, logged-in Supabase session (rejects
     anyone unauthenticated with a 401) — defense in depth, since this
     function is the only thing standing in front of a billed API.
  2. Reads the actual Gemini API key from a server-side secret
     (`Deno.env.get('GEMINI_API_KEY')`) that is set via the Supabase CLI and
     never appears in any file that ships to the browser.
  3. Forwards the prompt to Gemini and returns the response.
The browser's GeminiService class now calls this Edge Function (via
`supabase.functions.invoke(...)`, authenticated with the user's session)
instead of calling Google directly. The only thing that ever reaches the
browser now is a plain boolean feature flag (`VITE_AI_ENABLED=true`) — not
a secret, just an on/off switch for "use the real AI service instead of the
mock one." This was verified concretely by grepping the final production
JavaScript bundle for the actual key value — it is not present anywhere in it.

Other security practices worth mentioning: Row Level Security is enabled on
every single table in the database (Postgres itself enforces "a user can
only see/change their own rows" — even if the frontend had a bug, the
database is the real enforcement point, not just the UI); the Supabase anon
key is the only key that ships to the browser, by design, since RLS makes it
harmless on its own; `.env` files are gitignored and were verified to have
never been committed to git history before the project was made public;
and the YouTube API key (a lower-risk, intentionally client-side key) is
recommended to be restricted by HTTP referrer in the Google Cloud Console.

9. EMAIL MONITORING, IN FULL
--------------------------------------------------------------------------------

WHAT IT DOES
  With the learner's explicit permission (Gmail OAuth, read-only), the app
  can read their inbox and turn anything genuinely actionable — a scheduled
  interview, an exam date, a deadline, a meeting invite — into a real to-do
  task, without the learner re-typing it by hand. Everything else in a real
  inbox (newsletters, receipts, marketing, automated notifications) is read,
  classified as not actionable, and never shown — a real inbox is mostly
  noise, so showing nothing until something is confirmed worth attention is
  the deliberate default, not a missing feature.

HOW SCANNING AND CLASSIFICATION WORK TOGETHER
  Clicking "Scan Inbox" (Email page or Settings) does two things back to
  back: gmail-fetch-messages pulls the 50 most recent Gmail messages and
  stores any not already seen; classify-emails then reads every
  not-yet-classified row and, per email, asks Gemini whether the recipient
  needs to DO or PREPARE something because of it, returning a learning goal
  (or an empty string), an urgency level, and a confidence score. Only
  results scoring confidence > 0.7 with a non-empty goal ever surface to the
  learner. Classification runs up to 8 emails concurrently (a small bounded
  worker-pool, not a queue or job system) — the difference between a full
  50-email scan taking roughly two minutes one-call-at-a-time versus a few
  seconds.

TRUSTING (OR NOT TRUSTING) WHAT THE MODEL RETURNS
  Gemini's JSON output isn't taken on faith. Before anything from a response
  is used, it's regex-extracted into a clean JSON span (in case the model
  wrapped its answer in a sentence of prose despite being told not to) and
  validated against a zod schema; a response that doesn't pass is retried
  once with a fresh model call, and if it still doesn't validate, a plain
  hand-written fallback takes over instead of an AI response that might be
  malformed or fabricated. This applies to every Gemini call this feature
  makes, including the email-summary modal described below.

THE EMAIL PAGE
  Each actionable email shows a priority badge (high/medium/low, the same
  colors as the to-do list) and can be turned into a real to-do task with one
  click ("Add to Task List"), or all of them at once ("Organize into Tasks").
  Converted tasks get a due date offset by urgency (today / +2 days / +5
  days) rather than all landing on today, which is what makes them show up
  spread out sensibly on the Calendar instead of piling onto one day — the
  same to-do rows already power the Task List and Calendar, so nothing extra
  had to be built for that part. Clicking an email (rather than one of its
  action buttons) opens a modal with an AI-generated summary of what it's
  actually about — reusing the exact same summarizeDocument prompt PDF
  Intelligence already uses for document summaries — never the raw body text.

CONNECTING GMAIL, AND HOW IT'S KEPT SAFE (the same security discipline as
the Gemini key, applied to a much more sensitive credential)
  A learner opts in explicitly via Google's standard OAuth consent screen
  (Settings -> Connect Gmail), granting only the read-only gmail.readonly
  scope — this app can read mail, never send, delete, or modify it. The
  resulting access and refresh tokens are never stored in plain text: the
  gmail-oauth-callback Edge Function encrypts each one independently with
  AES-GCM (a fresh random IV per token, since reusing an IV under the same
  key is an AES-GCM correctness bug, not just a style nitpick) using a
  server-only secret before writing to Postgres — gmail_oauth_tokens only
  ever holds ciphertext. Row Level Security still restricts every row to its
  owner on top of that, as defense in depth. The one exception to the usual
  "forward the caller's own login" pattern is agent-cron-check, an optional
  scheduled function that can scan every connected learner's inbox on a
  timer with nobody logged in to forward a session from — it uses the
  Postgres service-role key instead (the one key in this whole project
  that's allowed to bypass Row Level Security) and is gated by its own
  separate shared secret header, since that function itself is the trust
  boundary rather than a user's session.

10. WEEKLY PLAN, IN FULL (a real autonomous feature, not just an AI reply)
--------------------------------------------------------------------------------

WHY THIS ONE COUNTS AS "AUTONOMOUS" AND NOT JUST "AI-POWERED"
  Most "AI features" in this app answer a question or generate content on
  request — genuinely useful, but the learner is always the one deciding what
  happens. Weekly Plan is different: clicking "Generate This Week's Plan"
  actually reaches into the database and moves things. It's the one place in
  the app where an action, not just an answer, happens on the learner's
  behalf — which is why it's the closer answer to "what's your autonomous
  agent" than the multi-agent system that got built and then removed earlier
  in this project's history (see git log around that decision if it ever
  comes up — the honest short version: five hand-rolled agent nodes were
  built, but only one of them was ever reachable from any real UI, so it was
  cut in favor of this, a smaller feature that's 100% real end to end).

WHAT ACTUALLY HAPPENS, IN ORDER
  1. Every incomplete to-do task that's either overdue or due within the next
     7 days is collected and sorted (highest priority first, then soonest
     due date first) — src/services/weeklyPlan.service.ts.
  2. Each one is greedily assigned to a day in the next 7, preferring its own
     due date if that day isn't already at capacity (3 tasks), otherwise the
     next open day, so nothing is invented — a task keeps its date unless
     keeping it would cause a pile-up. This is deterministic, ordinary
     TypeScript — no AI is involved in deciding the schedule itself, which is
     exactly why it's safe to let it actually write to the database instead
     of just suggesting something.
  3. Any task whose day changed gets its due_date updated for real in
     Postgres — this is the autonomous part. The count of how many moved is
     recorded and shown to the learner, never hidden.
  4. Read-only context is added: any active roadmap's tasks whose already-
     existing computed schedule (see section 5, roadmap scheduling) falls in
     the next 7 days are included for the AI to reference, but never moved —
     roadmap task dates are computed on the fly from hours/day, not stored
     per-row, so there's nothing to safely reschedule there anyway.
  5. Only now does Gemini get involved — given the finished, real schedule
     (never asked to invent one), it writes a short specific recap ("you have
     23 tasks this week...") and a one-line suggested daily rhythm. If Gemini
     is unavailable, the mock service returns an honest demo-labeled version
     of the same two fields — the schedule itself already happened either way.
  6. The result is saved to a new weekly_plans table and shown on the
     Dashboard: the recap, the rhythm tip, and a 7-day grid of what's due
     when, with roadmap-vs-to-do items visually distinguished.

WHY THE AI CALL REUSES ai-complete INSTEAD OF A NEW EDGE FUNCTION
  generateWeeklyPlanSummary is just one more method on the same AiService
  interface every other AI feature in this app already implements (mock +
  Gemini), so it automatically inherits the existing ai-complete Edge
  Function, the existing key-security model, and the existing offline-demo
  behavior — zero new backend surface for the "write a recap" half of this
  feature. Only the actual scheduling logic needed to be new code, and it
  runs entirely in the existing browser-side service layer since it's just
  ordinary Postgres reads/writes through Supabase, not something that needs
  a paid API key hidden.

11. ASK YOUR DOCUMENTS (RAG), IN FULL
--------------------------------------------------------------------------------

WHAT IT IS
  A chat-style page (/app/ask-docs) where a learner asks a question in plain
  English and gets an answer grounded in their own uploaded PDFs — not
  Gemini's general knowledge, and not one document at a time like PDF
  Intelligence's existing Q&A tab, but a real retrieval-augmented-generation
  (RAG) search across every PDF they've ever uploaded, with citations back to
  the specific document each part of the answer came from. This is the
  standard "real AI engineering" demo (as opposed to "call an LLM and print
  the response"), so it's worth being able to explain precisely.

THE PIPELINE, STEP BY STEP
  1. INGEST (unchanged): a PDF is uploaded, text extracted client-side via
     PDF.js, split into ~2000-character chunks, and each chunk saved as its
     own document_chunks row — this part already existed for PDF Intelligence.
  2. EMBED (new): right after chunks are inserted, the frontend fires a
     request to the document-embed Edge Function (fire-and-forget — a failure
     here doesn't block the upload, it just means that document isn't
     searchable yet and can be retried). That function calls Gemini's
     embedding model for every not-yet-embedded chunk (up to 5 concurrently)
     and writes the resulting vector into a new `embedding vector(768)`
     column, added via a migration that also enables Postgres's pgvector
     extension.
  3. RETRIEVE (new, on each question): document-ask embeds the learner's
     question with that same embedding model, then calls a Postgres function
     (match_document_chunks) that orders every one of that learner's chunks
     by cosine distance to the question's vector and returns the top 6 — a
     plain sequential scan, deliberately not a specialized ivfflat/hnsw
     index, since a single learner's personal document count is small enough
     that the extra index complexity wouldn't pay for itself yet.
  4. ANSWER (new): those 6 excerpts are numbered and inserted into a prompt
     that explicitly instructs Gemini to answer ONLY from them, citing
     inline like [1], and to say plainly when the excerpts don't actually
     contain the answer rather than falling back on outside knowledge. The
     response is validated (same regex-extract + zod-schema + retry pattern
     used everywhere else — see section 9) before it's trusted.
  5. CITE: the UI shows the answer via the same AiMarkdown component as
     every other AI surface in the app (so a code block or formula in an
     answer renders exactly like it does everywhere else), followed by a
     badge per source document actually cited, not just retrieved — if
     Gemini didn't use a candidate excerpt in its answer, its badge doesn't
     show, so the citations reflect what was actually used, not just what
     was searched.

WHY THIS DOESN'T USE A VECTOR DATABASE PRODUCT
  Postgres with the pgvector extension is already provisioned as part of
  Supabase — reaching for Pinecone, Weaviate, or a similar dedicated vector
  DB would have meant a second database, a second network hop, and a second
  set of credentials to secure, for a workload (one learner's personal PDF
  collection) nowhere near the scale where a specialized vector store
  actually outperforms pgvector. Same judgment call as not using LangGraph
  for the agent system (section 9) — reach for the heavier tool when the
  problem's shape actually needs it, not by default.

SECURITY: WHY A LEARNER CAN ONLY EVER SEARCH THEIR OWN DOCUMENTS
  match_document_chunks is a plain SQL function (not SECURITY DEFINER), so
  it executes with the same Row Level Security the caller's own session
  already has — even though the function also explicitly filters by
  p_user_id as defense in depth, RLS on document_chunks and documents alone
  already makes it impossible for the query to see another learner's rows,
  the same guarantee every other table in this app relies on.

12. CONCLUSION
--------------------------------------------------------------------------------

Ascend is a full-stack, AI-integrated learning platform built as a single
React SPA on top of Supabase, with no custom backend server except a handful
of small, purpose-specific Edge Functions. Its defining engineering decisions
are:
  - A strict service-layer boundary so every Supabase/AI call lives in one
    place, making the mock/real AI split (and any future backend swap)
    a change that never touches UI code.
  - Every AI-dependent feature works identically, with zero setup, via a
    deterministic, clearly-labeled mock implementation — while the real
    implementation is a disciplined set of structured-JSON prompts against
    Google Gemini, not a trained ML model.
  - Security treated as a first-class concern, not an afterthought: Row
    Level Security on every table, a billed API key moved server-side behind
    authenticated proxy functions, and Gmail OAuth tokens individually
    AES-GCM encrypted at rest.
  - AI output is never trusted blindly: every structured Gemini response is
    regex-extracted, schema-validated, and retried before use, with a
    hand-written fallback if it still doesn't hold up — and RAG answers are
    explicitly restricted to only the retrieved context, instructed to admit
    when that context doesn't contain the answer rather than guess.
  - Reach for the heavier tool only when the problem's actual shape needs
    it, not by default: pgvector (already provisioned via Supabase) instead
    of a separate vector database for RAG; a hand-rolled state machine
    instead of LangGraph for the email classification pipeline; a real,
    autonomous, deterministic scheduler (Weekly Plan) doing the actual work,
    with Gemini only writing the recap afterward — not the other way around.
  - A real automated test suite (CI-enforced) covering deterministic logic
    and AI service contracts, without ever depending on a live, billed model
    call to pass.

The result is a product that demonstrates the same engineering discipline
whether or not it's connected to a real AI provider — which is exactly the
property that makes it safe to hand to anyone (a reviewer, an interviewer, a
teammate) to run and evaluate immediately, with nothing hidden or faked.
